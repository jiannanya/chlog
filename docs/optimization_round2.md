# chlog 第二轮优化与验证

日期：2026-09-08。此次继续优化上一轮增加的同步开销、异步事件传递和 sink 注册分配。
保持原有调用接口、关闭时等待在途调用、异步刷新屏障和过载处理语义。

## 实现变化

1. **sink 列表读取不再操作共享引用计数。** logger 使用只追加、地址稳定的节点，
   发布末尾指针。一次同步分发或异步批次捕获末尾，新添加的节点不延长正在执行的遍历。
   节点由 logger 持有，在停止工作线程和等待在途调用后随对象销毁。
   注册新 sink 不再复制整份列表，累计列表构建开销从平方增长改为线性增长。
2. **批量出队直接构造输出事件。** 在释放任何槽位之前预留 vector 容量，
   移除中间事件移动；批次内递增槽位索引，批次结束后统一发布 head。
   logger 继续只预分配一个批次缓冲，消费完毕后释放正文占用的堆内存。
3. **保留精确容量并优化常见索引。** 二次幂容量使用位掩码；默认低优先级队列的
   `3 × 2^k` 容量使用常量除数余数计算，其他容量仍支持普通取模。
   测试覆盖 0、1、2、3、4、6、7、10、12、16、24、25、48、63、96、128。
4. **减少生产者争用。** 只读队列指针、生产者原子计数和消费者批次状态分开布局。
   异步接收计数从已经保留的队列位置取得，不再对每条成功提交执行独立的接收计数 RMW。
   运行中的统计快照仍可能观察到正在发布的事件；shutdown 后计数精确平衡。
5. **减少格式化入口开销。** `log()` 与 `log_at()` 各自只做一次级别过滤。
   无参数、无花括号的普通文本直接构造正文；转义花括号、自定义 formatter 和运行时
   格式错误仍交给 std/fmt 后端处理。
6. **空闲与刷新时间处理。** 禁用周期刷新时不再每批读取时钟，空闲检查间隔由
   100 ms 调整为 1 s；消息提交和停止仍通过信号量唤醒。正刷新周期的空闲等待按截止时间调整。
   超大正周期饱和到时钟最大时间点，极小负周期直接禁用，避免时间转换或加法溢出。

## 编译与正确性验证

| 构建配置 | 结果 |
|---|---|
| Windows Clang 17 Release，std::format | 9/9 通过 |
| Windows Clang 17 Release，fmt 11.1.4 | 9/9 通过 |
| Windows MSVC 19.38 Debug，std::format | 9/9 通过 |
| Linux/WSL GCC 13.3 Release | 9/9 通过 |
| Linux/WSL Clang 18，ASan + UBSan | 9/9 通过，无检测报告 |
| Linux/WSL Clang 18，ThreadSanitizer | 9/9 通过，无数据竞争报告 |

前八项为核心测试，第九项将库安装后在独立 CMake 项目中查找、编译并运行消费者。
安装消费者使用普通 Release 配置。六个安装目录中的头文件均与最终源码逐字节一致。
最终构建日志没有编译警告。

新增 `registration` 测试验证正在分发时的列表边界、sink 生命周期，以及同步、异步、
并行三种模式下四个生产者与 sink 注册同时执行。格式测试补充无参数字面量、转义括号、
运行时格式错误。配置测试覆盖 `milliseconds::min/max`。
异步测试还覆盖 8 KB 正文、嵌入 NUL、调用后复用原字符串，以及小队列反复回绕。

最终实现上，ThreadSanitizer 的 queue、async、parallel、concurrent、registration
五组各重复 20 次，共 100 次通过，包含大正文与嵌入 NUL 的异步用例。

20 个生产线程、300,000 次调用、四种 sink 的压力示例输出经独立 JSON 解析核对：
接收与完成均为 51,689，主动丢弃 248,311，最终队列为 0；300 条 ERROR 和 1,200 条 WARN
全部保留。示例开启低优先级丢弃策略；这次压力运行用于核验内容与计数，不作为吞吐比较。

Windows 本机 Clang 17 ASan 的运行库限制沿用[第一轮报告](optimization_results.md)说明；
内存及未定义行为检测实际在 Linux/WSL 完成。未新增 macOS、ARM 或 spdlog 对照验证。

## 测量方法

比较三个头文件版本：原始 Git 提交 `d63ceda126cc6165c8cf1101ae5f16db8978882d`、
第一轮结束时保存的头文件、本轮最终头文件。三者都使用本轮同一份 benchmark 源码，
以 Windows Clang 17.0.6、MSVC STL 14.38、std 后端和 `-std=c++20 -O2 -DNDEBUG` 编译。
硬件为 Intel Core i9-12900K。

三个版本交替运行五轮；每次计数测试 2,000,000 条，渲染与完整模板测试 100,000 条。
异步使用固定 65,536 槽、阻塞溢出策略并计入排空时间。所有非过滤计数用例均完成全部消息，
丢弃为 0。渲染到内存累计输出字节，不包含磁盘 I/O。

最终测量将各子进程限制在相同的逻辑处理器集合 0、2、4、6、8、10、12、14
（亲和性掩码 `0x5555`），测量时没有并行执行本任务的构建或测试。
较早出现过系统满载，受干扰的临时结果不用于本报告的性能表；系统其他任务仍可能影响最终计时。
报告使用中位数，原始各轮输出及头文件、benchmark 源码 SHA-256
保存在 [optimization_round2_benchmarks.json](optimization_round2_benchmarks.json)。

## 计数 sink 吞吐

单位：百万条/秒，越高越好。变化列比较本轮与上一轮。

| 场景 | 原始版本 | 上一轮 | 本轮 | 相对上一轮 |
|---|---:|---:|---:|---:|
| 单线程格式化 | 22.194 | 23.652 | 22.460 | -5.04% |
| 线程安全同步格式化 | 14.941 | 12.903 | 14.636 | +13.43% |
| 异步格式化，单生产者 | 3.996 | 3.587 | 3.397 | -5.30% |
| 异步格式化，四生产者 | 8.125 | 6.885 | 7.886 | +14.55% |
| 单线程纯文本 | 23.812 | 27.303 | 43.473 | +59.23% |
| 线程安全同步纯文本 | 15.557 | 14.689 | 25.337 | +72.49% |
| 异步纯文本，单生产者 | 3.970 | 4.029 | 4.685 | +16.29% |

线程安全同步、四生产者异步和纯文本场景取得收益。也存在明确回退：
单线程格式化吞吐下降约 5.0%，单生产者异步格式化下降约 5.3%。
这些场景没有获得一致提速；不能将局部收益推广到所有负载。

过滤用例耗时不足 1 ms，受调度和计时分辨率影响较大，原始数据保留其结果，
不据此推断过滤路径的稳定性能差异。

## 分配开销

以下是探针期间请求的累计堆分配字节，不是峰值活跃内存，也不是进程 RSS。

| 场景 | 上一轮 | 本轮 | 变化 |
|---|---:|---:|---:|
| 注册 16 个 sink | 29,088 B | 22,728 B | -21.86% |
| 注册 256 个 sink | 2,188,563 B | 363,968 B | -83.37% |
| 注册 1,024 个 sink | 30,854,163 B | 1,451,110 B | -95.30% |

注册 1,024 个 sink 的分配次数由 16,382 降为 13,330。
只追加节点会增加每个 sink 的固定节点存储，因此累计分配减少不等于常驻内存同比减少。
该探针包含 sink 自身和模板的构造，仅用于展示注册规模扩大后的分配趋势。

65,536 槽异步 logger 的构造/工作线程初始化仍请求 6,314,735 B，
与上一轮一致，相对原始版本的 9,888,510 B 减少 36.14%。
128 字符 logger 名称、预热后 100,000 条短消息的探针仍为 0 次分配、0 B。
这些数据限于指定配置；本轮没有测量整个进程的 RSS 或空闲 CPU 降幅。

## 复现入口

```powershell
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-release
ctest --test-dir build-release --output-on-failure
./build-release/chlog_bench_loggers --iters 2000000
./build-release/chlog_render_bench 100000
```

`_literal` 结尾的用例为无参数普通文本；其他计数用例仍格式化 `"v {}"`。
`REGISTRATION` 探针分别构建 16、256、1,024 个 sink，并在注册后确认每个 sink 都收到日志。
ASan、UBSan、TSan 和 fmt 构建方式见[第一轮报告](optimization_results.md)。
精确复现表格时还需使用报告注明的手工 `-O2` 编译参数、同一处理器亲和性和五轮交替运行方式。
